# Visibility recovery after interrupted interactions

On September 26 the owner requested an audit of cases where Knotch stays open when it should hide, or stays hidden when it should reveal. The audit found reproducible reducer traces and controller races in both directions. This follows the owner's pointer-exit minimisation preference recorded in decision 0002; the original handoff's focus-only keep-open rule is superseded by that preference.

## Confirmed failure paths and changes

- A display update cancelled the pending exit timer and discarded exit intent, leaving an interactive panel open with the pointer outside. It could also cancel a hover timer while retaining `pointerInTrigger`, preventing the next entry from arming a reveal. Display changes now reset stale pointer state while preserving departure intent. The controller reconciles containment after actual display or frame placement changes, including resolution changes on the same display.
- Keyboard activation followed by a dialog lock and focus loss could leave an unfocused preview without exit intent. The final unlock now settles that preview when the pointer is outside. Repeated focus loss and unpinning use the same exit eligibility rules; releasing a lock can also restore a cancelled hover dwell.
- Native drags can suppress normal mouse-exit callbacks. Clipboard drag, external drag, and resize completion now reconcile the endpoint before removing their interaction lock. Generation checks prevent an earlier external-drag exit callback from unlocking a later drag. Explicit hide and screen lock cancel the outstanding external-drag handoff timer.
- Deferred Clipboard insertion, new-tab shell-startup waits, and file-promise completion could select a tab and reopen Knotch after a later hide or other presentation change. They now capture a presentation revision and reject stale presentation/insertion work. A late valid promised image is still saved in local Clipboard history. Cleanup from an older Clipboard drop cannot unlock a newer drag.
- Only Ghostty input renewed the typing grace period. Panel key delivery now also renews it for Clipboard search and Settings controls, without consuming or redirecting the key event.
- Ghostty's own paste and clipboard-write consent alerts now use the same balanced system-dialog level handling as app-owned dialogs, so the high-level overlay yields while they are presented.

A shortcut-only activation still stays open until a real pointer departure, loss of focus, or explicit hide. Typing grace, active selection/composition, dragging, dialogs, and pinning retain their intentional holds. No terminal surface or process is replaced by these changes. Ghostty remains pinned at `982fe90d941e4b4aab4905ffcbcfdea60bd83343`.

## Evidence and limits

`scripts/test-models.sh`, `scripts/build.sh --test`, and `scripts/build.sh` passed. The model suite adds focused event traces for these cases alongside the existing 10,000 randomized transitions. The final native fixtures passed [49 overlay checks](../test-results/visibility-overlay.json), [47 Clipboard checks](../test-results/visibility-clipboard.json), and [12 Settings checks](../test-results/visibility-settings.json). Overlay checks exercise actual NSPanel state, a real NSTextField receiving its key while remaining open through typing grace, and retained Ghostty surface/PID. Pointer endpoints, display changes, and focus/lock transitions are controlled fixture inputs; they are not physical monitor or cross-app hover qualification. Clipboard checks include an immediate hide before queued same-tab and new-tab drops finish, with no insertion or reopen afterward.

The ad-hoc signed Release was installed to `/Applications/Knotch.app`, signature-verified, and restarted. Its executable SHA-256 matches the build: `eea48e3586e7143e67d6a429f0c01949708312305e6d575bd213daaa55487736`. Native UI automation opened the installed workspace and minimised it back to idle, with no shell. Build environment remains macOS 26.6.2 (25G83), arm64, Xcode 27.0 (27A266a), SDK 27.0, Swift 6.4, deployment target macOS 26.0; pinned engine requirements remain unchanged. Build warnings about absent App Intents metadata and upstream ImGui debug symbols did not prevent either build.

Physical monitor unplug/reconfiguration, full-screen Spaces, cross-app pointer/drag races, actual asynchronous floating-thumbnail promise delivery, and Ghostty consent-alert interaction remain unqualified in this run. The review also identified a possible held selection/composition lock if its release notification is never delivered; this was not reproduced and was not changed speculatively. Passing the tested traces does not establish that every possible OS event ordering is covered.
